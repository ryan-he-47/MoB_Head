# 推理速度/带宽基准：原生 lm_head+softmax vs 蒸馏 MoB 头

日期：2026-09-01 · 平台：本地 RTX 4060 Laptop（8GB）+ CPU · 脚本：`scripts/benchmark_decode.py`
动机：立项目标是消除 h×V matmul 与 V 维 softmax 的带宽瓶颈；本文给出实测与解析两组数字。
注：docs/08 原预留给集群 P3 报告，现集群报告顺延为 docs/09。

## 1. 解析值（每个解码步，bf16 骨干 + fp32 头）

| 路径 | 头部读取 | 头部 FLOPs | 端到端字节/token |
|---|---|---|---|
| native（lm_head+V-softmax） | **501.0 MiB** | 525.3M | 2.302 GiB |
| MoB K=32（P2 最终头，18.5M 参数） | **70.7 MiB（−86%）** | 37.1M（**14.2×↓**） | 1.882 GiB（**−18.2%**） |
| MoB K=128（B+A 配置，32.4M 参数） | 123.0 MiB（−75%） | 64.5M（8.1×↓） | 1.933 GiB（−16.0%） |

- 头部带宽降幅 ~4-7 倍；因为 Llama-3.2-1B 嵌入 tied，词表矩阵本就是共享的，收益是**每步不再整读 501MiB**。
- 该占比在量化下大体不变（骨干 int4 时词表表也 int4）——端侧量化部署同样享受 ~18% 的每步流量削减。
- 字节数未计 KV cache 读取（两条路径相同）。

## 2. 实测：头部单步延迟

**GPU（bf16 输入，fp32 头，CUDA 事件计时）**

| batch | native | MoB-K32 | MoB-K128 |
|---|---|---|---|
| 1 | 2.229 ms | 1.795 ms | 1.951 ms |
| 16 | 2.365 ms | 2.071 ms | 1.876 ms |
| 64 | 2.872 ms | 1.902 ms | 1.556 ms |
| 256 | 7.405 ms | **1.938 ms（3.8×）** | 3.072 ms（2.4×） |

- batch 1 时本机 GPU 是启动/延迟受限，二者接近；批量上来后原头的 V 维读权+softmax 立刻成为瓶颈（batch 256 时 3.8×）。

**CPU（fp32，batch 1）——最接近端侧的口径**

| native | MoB-K32 | 加速比 |
|---|---|---|
| 41.96 ms | 3.71 ms | **11.3×** |

## 3. 实测：端到端贪心解码（KV cache，256 token，不计 prefill）

| native | MoB-K32 | MoB-K128 |
|---|---|---|
| 30.6 tok/s | 34.1 tok/s（**1.115×**） | 33.8 tok/s（1.103×） |

- 本机 GPU 上端到端 +11%：因为 4060 带宽充裕，头部原只占每步 ~7% 时间。**带宽越受限的设备收益越大**（手机/NPU/低带宽内存）。
- 注意：该端到端口径里 native 用的是 argmax（免 softmax）；若 native 走采样（真 V-softmax），MoB 的相对优势会更大。

## 4. 对端侧小模型的价值判读

1. **CPU/端侧直接收益是数量级的**：头部 11.3× 加速（41.96ms → 3.71ms）。端侧 CPU 上原头的 V 维 matmul+softmax 是每步的主开销之一。
2. **带宽削减是结构性的**：每 token 少读 ~430MiB（K32），与量化方案正交、叠加生效。
3. **FLOPs 削减 8-14×**：NPU/低功耗芯片上直接转化为能耗下降。
4. 代价：当前蒸馏头的保真度差距（P2 水平 PPL 2.13×，见 docs/07）——应用价值兑现的前提是 B+A（集群 FineWeb-Edu 10B + 大头）把保真度差距收拢。

## 5. 补充：WSD 加宽头实测（2026-09-02，head = WSD 跑 step-100k checkpoint）

用户问"加宽头有没有慢太多"。架构与 docs/08 的 K=128 列相同（K=128/width 3072），用当前 WSD 在训头复测，结论一致：**加宽的代价在推理侧几乎不可见**。

| batch | native | MoB-K32 | MoB-K128（WSD 在训头） |
|---|---|---|---|
| 1 | 2.489 ms | 1.924 ms | 1.993 ms |
| 64 | 3.106 ms | 1.947 ms | 2.331 ms |
| 256 | 8.598 ms | 2.520 ms | 4.793 ms（仍快于 native 1.8×） |

端到端（256 token 贪心）：native 25.9 / K32 28.1 / K128-wsd 26.2 tok/s——K=128 与 native 基本持平（1.008×），比 K=32 略慢但仍无劣势。带宽/FLOPs 解析值不变（123 MiB、65M FLOPs）。

**CPU 端侧口径（用户要求补测，2026-09-02）**：

| 头部单步（CPU fp32 batch 1） | native | MoB-K32 | MoB-K128-wsd |
|---|---|---|---|
| 延迟 | 47.4 ms | 5.78 ms（8.2×） | 7.67 ms（**6.2×**） |

加宽到 K=128 后 CPU 单步从 5.8ms 涨到 7.7ms，但仍保持 6× 量级的头部加速。附带读数（CPU 端到端 fp32 贪心）：native 3.32 → K32 4.28 / K128 4.35 tok/s（1.29-1.31×）——CPU 上 MoB 路径端到端也已经反超原生。GPU 端到端读数存在 run 间波动（时钟/短测噪声），以头部单步与 CPU 数为准。
